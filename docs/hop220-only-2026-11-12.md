# Objetivo único: Apache Hop 2.20

Desde esta actualización del 12 de noviembre de 2026, el MCP se desarrolla exclusivamente para **Apache Hop 2.20.x con Java 21**. Maven compila directamente contra `2.20.0`; no existe un perfil adicional de compatibilidad ni un repositorio de snapshots. Los documentos fechados y las filas de versiones ya publicadas conservan sus resultados históricos.

## Cambios

- `pom.xml`: base `2.20.0`. Los plugins de prueba y H2 mantienen alcance `test`, y sus siete pruebas de componentes/JDBC se ejecutan en la verificación normal.
- Marketplace: mínimo `2.20.0`, máximo `2.20.999`, en ambos catálogos locales.
- Capacidades MCP: `tested_hop_versions` contiene únicamente `2.20.0`.
- Relaciones de ejecuciones: llamada directa a `Execution.getLaunchedById()`, eliminando el adaptador de reflexión para 2.19. Se conserva la interpretación prudente de documentos antiguos y el error tipado sin datos sensibles cuando falla la API nativa.
- CI y benchmarks: runtime 2.20.0 y un solo build ordinario; se elimina el job duplicado de snapshots. Se actualizaron las instrucciones de desarrollo, seguridad y compilación.

Compilación habitual:

```powershell
rtk mvn -B clean verify
```

En este equipo también está el script directo `D:\dev\build_hop_web\mcp\hop220-only\20261112\build.ps1`, que usa Java 21, la caché Maven local y temporales bajo `D:\dev\build_hop_web`.

## Verificación local

La ejecución completa terminó con **200 pruebas, cero fallos, cero errores y tres omisiones por enlaces de Windows**. Las siete pruebas de componentes y JDBC se ejecutaron sin omisiones. Se verificaron formato Java, índice Jandex, SBOM y exclusión de bibliotecas de Hop y de prueba del ZIP. El SBOM resuelve todas las dependencias `org.apache.hop` a `2.20.0`.

La prueba del plugin instalado en un directorio aislado usó las bibliotecas de Hop 2.20 de `C:\hop`, Java 21 y un proyecto descartable. Aprobó inicialización MCP `2025-11-25`, descubrimiento de 24 herramientas por defecto, configuración, validación, rechazo de argumentos inválidos, referencias, diagnóstico de rutas y cierre STDIO. `tools/list` ocupó 92.559 bytes. Los logs de aplicación permanecieron en stderr. Esta prueba no habilitó mutación ni ejecución y no utilizó proyectos ni bases de producción.

Se validó la sintaxis YAML de CI, del benchmark y de los dos catálogos con el parser SnakeYAML ya instalado, y la sintaxis de los scripts Node modificados. No se ejecutaron workflows remotos ni un benchmark de rendimiento nuevo.

La primera ejecución encontró una carrera en una espera de `HopExecutionManagerTest`: el estado de cancelación puede verse antes de que el controlador publique su resultado de timeout. La prueba ahora espera ambos datos antes de comprobar exactamente las mismas condiciones. No se cambió el comportamiento del gestor de ejecución ni se debilitaron sus aserciones. También se observaron bloqueos temporales de archivos de Windows al reemplazar una definición y limpiar una carpeta JUnit; sus reportes se conservaron en `first-failed-reports`, y la verificación completa posterior pasó. No se atribuye una causa externa concreta ni una corrección permanente a esos bloqueos.
